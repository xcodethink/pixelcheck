## Why this release was cut

A correctness fix had been sitting on `main` unpublished. That is the exact trap
the 1.4.0 release existed to escape — fixed in the repository, still broken for
everyone installing from npm — so it was cut as soon as the fix landed rather
than waiting for a natural batch.

## Fixed — the file lock could lose a write

Under contention, `withFileLock` and `withFileLockSync` could admit two
processes to the critical section at once.

The reclaim path treated "no holder could be read" as "this lock is stale" and
unlinked whatever lockfile sat at the path. But a null holder usually means the
file is simply *gone* — the previous holder released it between the failed
acquire and the read — so the unlink deleted the lockfile of whichever process
had acquired it in the meantime.

**Blast radius**: that lock guards the daily cost ledger, the result cache and
the history database. A lost update meant under-counted spend or a dropped run.
Every version up to and including 1.4.2 is affected.

### How it was found, and what was proved

It surfaced as a CI failure on an unrelated PR: `expected 58 to be 60` in the
cross-process lock test. The tell that this was not a slow runner — **every
child exited 0 and nothing timed out**, so two of sixty increments were
overwritten rather than skipped.

Evidence rather than inference:

- A standalone stress harness (12 processes × 60 iterations, effectively
  zero-length critical section) reproduced the lost update. The existing 3 × 20
  test cannot: a longer critical section hides the race entirely.
- Instrumenting the reclaim branch on the old code showed it firing **1567
  times in one run, every one on the null-holder path and none on a genuinely
  expired lock**.
- After the fix, the same harness: 10 rounds, 7200 increments, zero lost.
- The strongest confirmation came for free — the PR whose CI had failed went
  green on its next run, with the fix merged in and nothing else changed.

### On testing, stated plainly

The race lives inside one function call with no seam to interpose on, so it
**cannot be reproduced deterministically from outside**. Two candidate
regression tests were written and both were discarded rather than shipped as
reassurance:

| Attempt | Why it was discarded |
|---|---|
| Churn test at 12 × 60 × 3 rounds | Stayed green five times against the broken code |
| Before/after swap test | Behaves identically on both implementations |

What is guarded deterministically is the mechanism the fix adds.
`_reclaimIfUnchangedForTests` (following the file's existing `_setClockForTests`
seam) is covered by two tests that were **verified to fail when the identity
check is removed**. The churn test remains as a labelled smoke test, with a
comment saying plainly that it is not a regression guard.

## Changed — a third smaller package

| | 1.4.2 | 1.4.3 |
|---|---|---|
| tarball | 817 KB | **551 KB** (−33%) |
| files | 421 | **302** |
| unpacked | 4.6 MB | **2.6 MB** |

- **Source maps are no longer published.** All 119 pointed at `../../src/*.ts`,
  which `files` has never shipped, and `sourcesContent` was empty — so every map
  a consumer downloaded was unresolvable. 843 KB, 17.8% of the unpacked package,
  wasted since the first release. Still built locally for development; the
  remaining `sourceMappingURL` comment was tested under
  `node --enable-source-maps` and is silently ignored.
- **The emitted JavaScript no longer carries implementation comments.** The
  build runs two passes — `--removeComments --declaration false` for the
  JavaScript, `--emitDeclarationOnly` for the declarations. A single
  `removeComments: true` would have stripped JSDoc from the `.d.ts` files as
  well, removing IDE hover documentation for all 67 public exports. Measured,
  not assumed; `.d.ts` output is byte-identical.

  Honest about the security value: of the twelve identifier leaks that reached
  the 1.4.1 tarball, six were file-header JSDoc that TypeScript copies into
  `.d.ts` regardless. `lint:no-internal-refs` remains the control; this narrows
  the surface behind it.

## CI

`darwin-x64` coverage is back, on `macos-15-intel`.

The matrix had dropped Intel macOS on 2026-07-26 because those jobs sat in
`queued` indefinitely and three PRs merged with permanently pending checks. The
diagnosis stopped at "GitHub no longer schedules Intel runners for this repo".
The actual cause was that GitHub **retired the `macos-13` image on
2025-12-04**, and a supported replacement has existed since 2025-09-19 — free on
public repositories. The accepted gap did not need accepting.

This matters because `better-sqlite3` and `sharp` ship distinct prebuilt
binaries per architecture, so an arm64-only matrix cannot catch a native-module
regression on Intel.

`macos-15-intel` is the last x86_64 image GitHub will offer and is removed in
**August 2027**; `ci.yml` records that deadline so the entry is dropped
deliberately next time rather than by surprise.

## Release pipeline

`release.yml` now runs on Node 22 with npm upgraded past 11.5.1, which npm
trusted publishing requires. Node 22 bundles npm 10.9.x, so the bundled version
is not sufficient and the explicit upgrade step is load-bearing.

This release still published with `NODE_AUTH_TOKEN`; the workflow prefers OIDC
whenever it is available, so the switchover is safe in either order.

## Rollback plan

npm tarballs cannot be unpublished after 72h; rollback is fix-forward.

- **Code**: `git revert 12cf06c` on a branch → PR → merge.
- **npm (within 72h, emergencies only)**: `npm unpublish pixelcheck@1.4.3`, then
  `npm dist-tag add pixelcheck@1.4.2 latest`.
- **npm (after 72h)**: `npm deprecate pixelcheck@1.4.3 "use 1.4.4"` and ship a
  patch.
- **Do not roll back to escape a problem in this release.** 1.4.2 and earlier
  carry the file-lock defect.

## Follow-ups

- **Trusted publishing still needs its npmjs.com side configured** — package
  settings → Trusted publisher, with organisation `xcodethink`, repository
  `pixelcheck`, workflow filename `release.yml`, environment empty. npm does not
  validate these on save, so a typo only surfaces as a failed publish. Once a
  release has published via OIDC, remove `NODE_AUTH_TOKEN` from `release.yml`
  and delete the repository secret.
- **`NPM_TOKEN` expires around 2026-08-31**, roughly five weeks out. That is the
  deadline the trusted-publishing work is racing.
- **The `macos-15-intel` jobs are not required checks.** They run, but a failure
  does not block a merge, so `darwin-x64` coverage is advisory rather than
  enforced. Adding them to branch protection would close that.
- **`@ai-sdk/provider-utils`** (17 low) clears when upstream stagehand updates
  its `@ai-sdk` dependencies. Out of production scope.
