# PixelCheck v1.0.1 — Critical Hotfix

**Released**: 2026-05-02

A same-day patch release fixing one P0 ship-blocker that broke `pixelcheck run` for every fresh `npm install pixelcheck` user, plus six smaller documentation-accuracy and tooling fixes uncovered by a deep post-publish audit.

**No API changes. No config changes. Pure bug fix per SemVer.**

If you installed v1.0.0 yesterday and tried the Quick Start, you almost certainly hit `[FATAL] Personas directory not found` — that's B1 below, and it's gone in v1.0.1. **Upgrade strongly recommended for all v1.0.0 users.**

---

## tl;dr

```bash
npm install -g pixelcheck@latest
# Quick Start now actually works:
pixelcheck init my-app --name "My App" --url "https://my-app.com"
pixelcheck run --dry-run     # ← prints persona × scenario matrix instead of crashing
```

## What broke in v1.0.0 (and why dogfood missed it)

The v1.0.0 `package.json files: [...]` shipped only `dist/`, `docs/schemas/`, and the four governance docs. **`personas/` and `scenarios/` were not in the npm tarball.**

Meanwhile the `pixelcheck init` command's post-scaffold message read **"Built-in personas (6) will be used automatically"** — implying bundled personas existed. They did not. On the next `pixelcheck run`, `loadPersonas()` would throw `[FATAL] Personas directory not found`. Reproducible 100% on every fresh install.

The `dogfood.yml` workflow that exists specifically to catch this class of "built locally, broken when installed clean" packaging bug only tested `--help`, `doctor`, and `init` — three commands that don't touch personas. **The first command that loads personas is `run`, and `run` was never in the dogfood matrix.** v1.0.1 adds it.

(Compounding the problem: `dogfood.yml` itself still invoked the pre-rename `ai-audit` binary instead of `pixelcheck`, so the workflow couldn't even start. That's B2.)

## All seven fixes

### B1 (P0 ship-blocker) — bundle personas + scenarios

- `package.json files: [...]` now includes `personas/` and `scenarios/`
- `cli.ts` adds a `resolvePersonasPath()` helper used by all three `loadPersonas()` call sites that falls back to `node_modules/pixelcheck/personas/` when the project has no local `personas/` directory
- Tarball: 590 KB / 333 files → **608 KB / 362 files** (still well under the 1 MB hard gate)

### B2 (P0 CI broken) — dogfood.yml stale binary name

- `.github/workflows/dogfood.yml` updated five `npx ai-audit` references to `npx pixelcheck`
- Without this, every PR landed after the rename failed CI on the dogfood step

### B3 (P1 doc accuracy) — "17 MCP tools" → 12

The MCP server's `ALL_TOOLS` array exports **12 tools**: 5 primitives (`see` / `act` / `extract` / `judge` / `compare`) + 2 audit presets (`audit_url` / `explore_url`) + 5 meta (`list_personas` / `list_scenarios` / `list_capabilities` / `calibrate_critic` / `get_last_report`). Five user-facing docs incorrectly claimed 17 — fixed across README, `launch-post.md`, `launch-post-zh.md`, `show-hn.md`, `release-notes/v1.0.0.md`.

### B4 (P1 doc accuracy) — "15 countries" → 17

The 18 bundled personas span 17 unique country codes (BR / CN / DE / FR / GB / ID / IN / JP / KR / MX / NG / RU / SA / TH / TW / US / VN). README + launch posts + release notes corrected.

### B5 (P2 cosmetic) — dynamic post-init persona count

`cli.ts` line 508 hardcoded `Built-in personas (6) will be used automatically.` Now uses a `countYamlFiles()` helper that reads the bundled `personas/` directory and reports the actual count (currently 18). Will stay accurate as bundled personas grow without further code changes.

### B6 (P2 doc accuracy) — ADR count + script systems

- `release-notes/v1.0.0.md` claimed "28 ADRs"; actual count is **33** (ADR-001 … ADR-033). Corrected.
- All 5 docs claimed "5 script systems (Latin / CJK / Arabic / Cyrillic / Devanagari)"; the Thai persona's locale `th-TH` uses the Thai script, which was missing from the list. Corrected to **6 script systems (Latin / CJK / Arabic / Cyrillic / Devanagari / Thai)**.

### B7 (newly discovered during dogfood) — invalid scaffolded scenario

`pixelcheck init` generated a `00-smoke.yaml` whose three steps lacked the required `id` field, causing `loadScenarios()` to throw a Zod validation error. The init template now emits `id: visit-home`, `id: capture-homepage`, `id: assert-homepage-loads` for the three default steps. Existing v1.0.0-init-ed projects need either a fresh `pixelcheck init <new-dir>` or a hand-add of `id:` to each step.

## Regression prevention (added in v1.0.1)

`.github/workflows/dogfood.yml` gains a new step:

```yaml
- name: Verify pixelcheck run --dry-run loads bundled personas
  working-directory: …/test-project
  env:
    ANTHROPIC_API_KEY: sk-ant-fake-not-a-real-key-just-for-cli-gate
    AUDIT_AUTO_CONSENT: "1"
  run: |
    OUTPUT=$(npx pixelcheck run --dry-run 2>&1) || EXIT=$?
    if echo "$OUTPUT" | grep -q "Personas directory not found"; then
      echo "::error::REGRESSION: bundled personas not loading (B1 in v1.0.0)"
      exit 1
    fi
```

This step would have caught B1 + B7 before v1.0.0 publish; from v1.0.1 onward every PR is gated on it.
